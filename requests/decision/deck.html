Start with a concrete contrast: asking a chatbot to write an explanation versus asking a model which queue should receive a ticket. This deck is an introduction, not a performance comparison.

The category / What are decision models?

Intelligence that returns a decision

A decision model evaluates supplied evidence against bounded questions and returns typed values and probabilities, rather than an open-ended written response.

Generative task

“Write a reply to this customer.”

The output is a new piece of content.

Decision task

“Which team should handle this message?”

The output fits a defined answer space your code can use.

Classification, routing, prioritization, and evaluation inside software. Not a replacement for every reasoning or generation task.

Sources: System One concepts · OpenAI Decisions overview

Introduce the category before the products. Classification is not new; the focus here is natural-language-defined, bounded judgments exposed as reusable AI primitives. A generative model with JSON output can also classify, but a constrained wire format alone does not establish a decision-focused inference architecture.

Use cases / Where a focused judgment helps

Small decisions. Everywhere in software.

Route requests

Which team, queue, model, or tool fits this request?

Prioritize work

How urgent is this ticket or incident on our rubric?

Flag for review

Does this order contain indicators that warrant a closer look?

Evaluate outputs

Does this agent's answer meet the supplied acceptance criteria?

Guide workflows

Is there enough evidence to continue, retry, or escalate?

Organize content

Which category fits this document, and how relevant is it?

Best fit: evidence is available, the answer space is bounded, and your application knows how to use the result.

Sources: System One workflows · OpenAI Decisions use cases

Use this third slide to connect the category to practical work before discussing vendors. Routing and categorization use choices; urgency and relevance use scores; acceptance checks and evidence gates use predicates. These are judgments, not permissions: keep authorization, inventory checks, and human approval in deterministic application code. A risk flag is a request for review, not proof of wrongdoing.

Origins / Jev and System One

Jev introduced the System One class

October 19, 2026

TypeSafe AI announced Jev in early access, introducing “System One” as a class of models for fast, structured decisions.

Built around the decision

A decision-focused architecture, parallel probability outputs, and training for calibrated decisions instead of generated prose.

TypeSafe describes Jev as the first System One model. This is the origin of its named class, not a claim that AI classification began with Jev.

Sources: TypeSafe's Jev announcement · Jev introduction

Attribute the origin claim to TypeSafe's announcement and documentation. Jev is named after William Stanley Jevons. Jev accepts text, including JSON and arrays of text, not images, audio, or video. Microsoft-Decision-1 and OpenAI Decisions are separate offerings, not demonstrated descendants of Jev's weights, architecture, or training recipe.

The name / Fast, focused judgment

Why “System One”?

System 1: fast judgment

“Does this ticket request a refund?”

A focused determination given the relevant context.

System 2: deliberation

“Investigate why refunds increased and propose a plan.”

A multi-step task requiring investigation and synthesis.

The name borrows Kahneman's fast/slow thinking metaphor. It is not a claim that a model has a human mind.

Source: TypeSafe: System One

This is a workload distinction, not a universal taxonomy of neural architectures. Fast does not mean infallible. A decision model can hand ambiguous cases to a reasoning model or human rather than trying to solve an entire workflow in one judgment.

Predicate / Noul: “Is this true?”

Express eligibility

“Is this order eligible for express fulfillment based on inventory, destination, and risk?”

A probability, not a verdict

Illustrative answer: 0.93

An estimate that the condition is true; your code chooses what to do with it.

predicate in OpenAI Decisions; noul in Jev and Microsoft-Decision-1.

Specify the condition clearly. Missing evidence is not automatically proof that it is false.

Question 3 of 3 / Score

Score: “How much, on this rubric?”

Define an ordered scale, not a vague “rate this out of ten.”

IndexUrgency levelIllustrative probability
0Low: no time pressure0.05
1Normal: routine shipment0.15
2High: shipping cutoff approaching0.60
3Critical: commitment immediately at risk0.20
Score = Σ index × probability = 1.95
A weighted position on this 0–3 scale, not a 65% chance of urgency.

Sources: Jev score · OpenAI score · Microsoft score. Synthetic values.

The arithmetic is 0 times .05 plus 1 times .15 plus 2 times .60 plus 3 times .20, or 1.95. The scale runs from zero to three, not zero to one hundred. A score is not the probability that a condition is true. Treat it as rubric-based ordering, not an absolute measurement of urgency.

How they work / Jev's published inference approach

Parallel decisions, not a paragraph

Generative response

Produce successive text tokens, each conditioned on earlier tokens. Parse the output if your code needs a decision.

Jev's published approach

A decision-focused architecture and parallel sampler produce bounded outputs. Questions evaluate independently against the same state.

Conceptual path: encode context + questions → evaluate allowed outcomes → return typed values and distributions.

The path is a teaching abstraction, not a disclosed layer diagram. Do not assume Jev's implementation applies to other vendors.

Sources: Jev announcement · Parallel question evaluation

The announcement describes a new architecture and parallel sampler but the sources cited here do not provide a full layer-by-layer specification, parameter count, or exact forward-pass count. Avoid inventing an encoder, classification head, or softmax implementation. Questions in one Jev call are independent: one answer is not fed into another. Use a second call when a later question needs an earlier answer. JSON mode in an LLM constrains text output; it does not by itself establish this inference architecture.

How they learn / Decisions and calibration

Optimize the uncertainty, too

RLHF

Human feedback: optimize responses people prefer.

RLVR

Verifiable rewards: optimize outcomes that can be checked.

RLCD

TypeSafe's reinforcement learning for calibrated decisions: optimize decisions and their probabilities.

If a model assigns 0.8 to many events, calibration asks whether roughly 80% of those events occur.

A population-level property, not a guarantee about one answer. These are training objectives, not a complete or exclusive training recipe.

Source: TypeSafe's AI primer

Attribute RLCD to TypeSafe, not to Microsoft-Decision-1 or OpenAI. The public primer does not disclose a complete reward formula, dataset, or training implementation. Evaluate calibration on representative local data, especially after a domain shift. Constrained outputs prevent arbitrary prose; they do not prevent incorrect classifications.

Why fast / Less output work on the critical path

Decide instead of writing the decision

Bounded outputs

Evaluate defined outcomes instead of generating a paragraph and then extracting a judgment.

Parallel evaluation

Jev outputs probabilities in parallel, rather than producing text tokens one after another.

Fewer round trips

Ask independent questions about the same evidence together instead of making a series of API calls.

OpenAI documents “about 10x faster” than its Responses API. This is a vendor claim, not a cross-vendor benchmark or a latency guarantee.

Input length, question count, model, load, and network location still matter. Measure end-to-end p50/p95 latency and decision quality on your workload.

Sources: Jev's parallel sampler · OpenAI speed claim · Foundry locality guidance

The speed explanation is about avoiding autoregressive output work and serial orchestration, not eliminating the cost of reading context. Parallel inference is documented for Jev; do not ascribe the same implementation to every decision API. Jev's launch also advertises much larger speedups under selected conditions, but they are not comparable to OpenAI's claim. No benchmark was run for this presentation. Related questions that need an earlier answer require a later call.

Economics / What cheaper judgments unlock

Same routing question. Different costs.

Task: “Which team should handle this ticket?” Assume 1,000 billable input tokens per request, including evidence and instructions. Generative calls return only the category in 20 output tokens, with reasoning disabled.

Model and useInput / 1M tokensOutput / 1M tokens1M decisions
GPT-6 Sol / generative Responses$2.00$10.00$2,200
GPT-6 Luna / generative Responses$0.10$0.50$110
Jev 1.14 / decision model$0.042Free typed output$42

Cost = input tokens × input rate + output tokens × output rate, divided by 1M. At this volume: 1B input tokens, plus 20M generated output tokens for Responses.

What this unlocks: evaluate every event instead of sampling; check more independent dimensions; reserve expensive reasoning and human review for ambiguous cases.

Jev is about 2.6× cheaper than the efficient generative baseline here, not universally 50× cheaper. USD standard uncached list rates, checked Oct 27, 2026; no batch discounts, retries, tools, or taxes. Assumed token counts, not measured quality-equivalent results.

Pricing: OpenAI standard rates · Jev models and input-only billing

Arithmetic per call: Sol = (1000 × 2 + 20 × 10) / 1,000,000 = $0.0022. Luna = (1000 × 0.10 + 20 × 0.50) / 1,000,000 = $0.00011. Jev = 1000 × 0.042 / 1,000,000 = $0.000042. Multiply by one million requests for the table. The budget ratio versus Luna is 110/42 = 2.619, or about 61.8% less inference spend. Sol is a more capable general-purpose baseline, not the cheapest way to classify; that is why the efficient Luna baseline is included. Luna also powers OpenAI Decisions, but this row specifically prices its generative Responses mode with reasoning.effort none, not the Decisions API. Jev still returns serialized JSON, but does not charge output tokens. The same ticket, policy, and allowed categories are the semantic task; equal assumed billable counts do not imply identical tokenizers or equivalent accuracy. No long rationale is added just to inflate the generative cost. Compare error cost, calibration, retries, engineering, and human escalation before switching. More checks also add question-input tokens, so they are not free. Prices here are direct-provider list prices, not an Azure pricing quote.

Another option / Microsoft-Decision-1

A decision model in Microsoft Foundry

What it does

Judges text or JSON for classification, routing, ranking, grading, and binary decisions. Returns numbers and probabilities, not a written rationale.

How you call it

Send state and a named questions object. Use noul, choice, or score.

POST /providers/microsoft/v1/systemone
The model field is your Foundry deployment name.

Source: Deploy and use Microsoft-Decision-1

Microsoft-Decision-1 is a model offering, not the name of the OpenAI API. Availability depends on deployment and region. Its similar question vocabulary does not prove common lineage or implementation with Jev. Use the resource endpoint and authentication described in the deployment guide.

Another option / OpenAI Decisions API

A purpose-built API for judgments

What it does

Evaluates text, images, and JSON. Returns a predicate probability, a choice, or a score with a distribution over levels.

How you call it

Send input and a questions array. Each question has a name and a type.

POST /v1/decisions on OpenAI
POST /openai/v1/decisions on a Foundry resource

Current OpenAI guide: gpt-6-luna. Confirm the model or deployment required by your endpoint. Use Responses for generated content or custom-schema extraction.

Sources: OpenAI Decisions guide · Availability in Foundry

OpenAI Decisions is an API surface backed by a supported model, not an architecture name. The local collection uses the Azure route. Jev and Microsoft-Decision-1 documentation here describe text and JSON, so image support should not be generalized to all three options.

Put it to work / Keep control in code

Typed does not mean true

  • Define: atomic questions, complete options, concrete rubrics.
  • Evaluate: labeled cases, hard negatives, missing evidence, and domain shifts.
  • Measure: decision quality, calibration, latency, and cost.
  • Control: deterministic policy checks, explicit review paths, and audit logs.
Use a decision model for a bounded judgment.
Use a reasoning model or human when the task needs investigation or explanation.

Further reading: System One workflows · Foundry threshold guidance

There is no universally safe probability threshold. Evaluate false positives and false negatives against the real business costs. Do not treat a model's probability as a security boundary or a substitute for authentication, authorization, deterministic validation, or human approval.
